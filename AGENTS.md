Shared contract version: 13

Every agent uses this same repo-work contract. Local repo `AGENTS.md`/`CLAUDE.md` files only point here and to `RULES.md`.

Follow the prompt-local request-fidelity rule in `RULES.md`.
- Immediately after that fresh-chat bootstrap, inspect `source_freshness.canonical_checkout`. If it is available and `coherent` is false, run `C:\Users\Lauri\.agents\Sync-AgentRulesCheckout.ps1` once before selecting repo work or relying on the serving checkout for current shared behavior. An exact `head_matches_remote_main` false value while `coherent` is true is diagnostic cache-lag evidence only and does not require sync. The default sync may fast-forward only a clean behind `main`; `DIRTY_BLOCKED`, `AHEAD_BLOCKED`, `DIVERGED_BLOCKED`, or other failure stays fail-closed. Do not add Git fetch/convergence work inside bootstrap itself, create a watcher/scheduler, hard-reset the serving checkout, or continue as though stale local policy were current. Attribute the blocking state and use the existing preserve-then-converge `-Repair` path only when serving convergence is actually required and exact collision/foreign-work safety permits it.

This is worker work-context, not bootstrap expansion; do not make it per-tool ceremony or a broad Vault scan. Historical memory/timeline informs the approach but never replaces current repo/runtime evidence.
- Immediately before the first mutation in a target repo, inspect that repo's branch/HEAD and dirty state, resolve the known matching issue/PR or do one targeted lookup if none is known, and inspect only the exact Busy scopes needed for the mutation. If relevant dirty work already exists, attribute and preserve it rather than piling unowned edits onto it. Do not use broad issue/PR history listings or repo fetches as startup ritual.

Before mutating `organicoverlords/agents`, run `Sync-AgentRulesCheckout.ps1`: a clean behind `main` fast-forwards to current `origin/main`, while dirty/ahead/diverged state fails closed. Product-repo `README.md`, North-Star paths, `docs/**/*.md`, and similar legacy locations are pointer surfaces only and must not carry competing prose. Artifact-bound evidence/provenance notes stay with their artifacts. Do not refresh, overwrite, or clean dirty product work merely to read documentation.

If the worker cannot establish all of those coherently, it must not touch that stack component; resolve the missing context first. Understanding one local file/service is not sufficient stack understanding.

## Swarm-friendly issue lifecycle
- **One issue, one outcome.** Use the existing GitHub issue as the shared work/convergence record. A parent convergence issue composes a milestone across several owners; child issues own bounded implementation or proof. Do not turn issues into a queue, worker assignment system, or one issue per checklist row.
- **Populate the current plan for simultaneous entry.** Put a compact current-plan block before long detail: authority/goal, existing implementation/PRs/checkpoints, remaining required results, and for multi-contributor work a small table or equivalent that names each required result, existing WIP/owner, exact logical files/resources and serialization boundary, acceptance evidence, and patch -> proof -> integration handoff. Expose multiple real non-overlapping contribution boundaries only where they genuinely exist.
- **Enter by reconciling, not inventing.** A worker entering the issue reconciles the current body, recent material comments, linked PRs/commits, exact claims, existing WIP, and immutable checkpoints, then prefers reuse/review/proof/integration of matching work. Select a new output only for an uncovered required acceptance gap. At a meaningful checkpoint/handoff, record branch plus immutable commit when available, validation already performed, unresolved blocker/finding, and next integration action; no heartbeat comments or duplicate status notes.
- **Update issues by the same logic used to create them.** Evidence-only progress belongs in a dated comment. A material scope, priority, acceptance, or direction change updates the issue's current-plan block so the next worker does not have to reconstruct direction from comment archaeology. Treat concurrent edits to the issue body as a shared serialization boundary under the existing exact-resource collision rules; comments may remain concurrent evidence.
- **Route user direction to the smallest existing authority.** A local instruction changes the affected issue/WIP only. A milestone or priority change updates the parent convergence issue and reconciles affected children/WIP. A real product-direction change updates the canonical North Star/direction document first, then the parent convergence issue. The worker that receives a material user-direction change owns this reconciliation before continuing; current explicit user direction outranks stale prose.
- **No orphaned work.** Before completing a material current-plan update, account for every active child issue, PR, branch/commit checkpoint, or proof artifact named by the previous plan. Each must be retained, retargeted with its still-valid contribution, blocked with a concrete gate, superseded by an exact successor/canonical path, or closed. Never silently drop useful WIP because the plan changed; preserve unique commits/artifacts and link the successor when work is superseded.
- **Issue-wall recovery is worker-owned.** If the current issue/parent appears exhausted, stale, overconstrained, or has no ready contribution, do not ask the user to seed, curate, reprioritize, or repair the issue graph. Reconcile the current North Star/parent acceptance against live main/runtime evidence, linked PRs, checkpoints, and existing children. Close or supersede finished/duplicate paths, retarget still-valid WIP, refresh the parent current plan and Project status, and create a new bounded child issue only for a real uncovered acceptance gap with no existing owner. If the parent acceptance is actually satisfied, close/advance it and continue from the next existing North-Star priority. Do not change the North Star merely to manufacture work; change product direction there only when explicit user direction or a genuine authority correction requires it.
- **Project active delivery into Stack Delivery.** `organicoverlords` Project #1 (`Stack Delivery`) is the existing cross-repo delivery projection; the owning issue/PR remains the work authority. Add active tracked delivery issues that matter to the current objective and keep `Status` current at meaningful plan/handoff/merge/proof boundaries: `Idea` = candidate only, `Shaping` = goal/acceptance still being resolved, `Ready` = accepted and actionable with no current WIP, `Active` = implementation/integration underway, `Review` = an exact patch/PR is awaiting review or landing, `Proof` = implementation has converged and acceptance proof remains, `Blocked` = that issue outcome cannot currently advance because of a concrete gate, and `Done` = closed/accepted. A parent may remain `Active` while one child is `Blocked`. Never use project status as ownership, admission, scheduling, or a reason to wait.
- **Use GitHub-native relationships as navigation.** When an issue is genuinely a bounded part of a parent convergence issue, record it as a native sub-issue so Project #1's `Parent issue` and `Sub-issues progress` fields work automatically; keep the parent current-plan table because it explains boundaries and acceptance. Pull requests reference their owning issue so `Linked pull requests` is useful; do not add every transient PR as a project item unless the PR itself is a cross-repo delivery object.
- **Use labels and milestones semantically, never as worker state.** Prefer a small stable label vocabulary for product/domain/type/risk such as `gameplay`, `acceptance`, or `performance`; do not encode worker identity, liveness, Busy ownership, or temporary assignment in labels or assignees. Use an existing repository milestone only when it genuinely names the delivery milestone; do not invent or force a milestone merely to mirror Project status. When a material plan change alters these semantics, reconcile the Project/relationship/label projection in the same update so it does not become stale.
- **Sanity-check convergence, not permission.** Before expanding scope or creating new WIP, compare the requested direction with current main/runtime evidence and the parent acceptance result: is the actual product/system getting better, does existing WIP already cover the gap, is the current bottleneck implementation or proof/integration, and can two simultaneous entrants choose useful nonoverlapping outputs and know what must serialize? Repair a stale plan when needed. This is a bounded design check, not a new approval gate or mandatory orchestrator.
- **Handoff and close cleanly.** The current exact mutation claimant composes overlapping contributions into one coherent patch. Define the handoff from patch to proof to integration with an explicit result/reference. Verified useful work should converge through the normal PR/integration path; stale duplicate paths are closed/superseded instead of becoming shadow backlogs.
- **Small issues stay small.** An ordinary one-owner issue can use compact bullets for Goal, Existing WIP, Acceptance, and Next handoff. Add the fuller contribution map only when several workers or owners genuinely need it.

## Doing the work
- For tracked engineering work that already uses an issue, use that issue as the shared coordination record and work identity, and reference it from meaningful branches/PRs/commits/checkpoints. A bounded local read/write/update or other prompt-local operation does not require creating or touching a GitHub issue merely for bookkeeping.
- A lane, branch, worktree, checkout, editor, build slot, route, or Busy claim is an execution surface/resource, not worker identity and not the task. Many agents may contribute to the same issue concurrently.
- Before each shared mutation, claim only the exact files/resources being changed through BusyCoordinator; do not turn the issue, lane, checkout, or Busy into a repo-wide lock.
- Busy mutation idempotency is per semantic mutation: never reuse one `--operation-id` across different claim, release, heartbeat, or recovery operations/scopes. Reuse an operation ID only to deliberately replay the same semantic operation. If key reuse causes a partial multi-scope result, reconcile the scopes that actually registered, clean up only owned residue, and fix the caller/helper so the next worker cannot repeat the same trap.
- Busy stale/orphan reclaim is routine. `inspect <exact-scope>`; if the owner is positively attributable, has no live child process, and has had no MCP process activity for at least 60 seconds, CAS-recover with the inspected old actor and exact timestamp: `busy-python.cmd recover <old-actor> <scope> --expected-claim-timestamp <timestamp> --operation-id <unique-id>`. `claim_changed` or newer activity cancels recovery. On success, claim the same scope under the current actor with a new operation ID and continue. Never rediscover this procedure during live work.
- If the current execution surface is dirty, stale, unsafe, unusable, or contains foreign/unique work, preserve it and leave the conflicting state intact. Continue through another already-existing safe supported surface or other useful work that materially advances the user's established goal. A decision-ready blocker is not a valid yield merely because no ready in-scope contribution remains; only the actual stop conditions in `RULES.md` permit yield. Do not manufacture unrelated work merely because the current surface cannot safely mutate.
- Do not create a fresh lane/worktree reflexively to escape an inconvenient current surface. Reuse safe existing supported surfaces and preserve useful warm state.
- Choose the highest-value load-bearing action that advances the current user objective. Existing unfinished relevant WIP should be repaired, proved, integrated, closed, or superseded before avoidable parallel WIP is created. Do not sit on CI, review, a Busy claim, a build slot, or another worker when another ready required contribution can advance the same established objective.
- Reuse the repo's existing supported entrypoints and wrappers. If a supported path required by the current request is broken, fix that owner rather than bypassing it with a parallel path; do not turn an unrelated broken path into work merely because it was discovered.
- Debug owner-first, not search-first. When the owner/entrypoint is known, use the exact error plus the smallest owner contract/source to form one hypothesis and one discriminating check. Do not fan out into wrapper/runbook/task/filesystem archaeology unless that specific unknown remains unresolved. A rejected low-level call does not justify inventing a parallel recovery path.
- A heavy wrapper is not current safety authority merely because its filename is canonical. Before build/runtime/render/GPU launch from a worktree that may be stale, resolve the repo's current supported heavy entrypoint from an already-existing refreshed execution surface; if it can target another project/worktree root, run that current wrapper against the preserved target instead of the stale branch-local copy. If current safety ownership cannot be established, fail closed; continue only other work already required by the current request, otherwise yield. Never refresh, overwrite, or clean foreign/dirty target state just to make the wrapper current.
- Make coherent changes and validate with the cheapest evidence sufficient for the requested claim. Do not poll unchanged state. When a required external/build/CI action is in flight, leave a checkpoint if needed and advance another ready in-scope contribution; return to the in-flight result only when it can change the next action. Do not manufacture unrelated adjacent work merely to keep a manual turn alive.
- Before sending an MCP `start_process` command, normalize obvious PowerShell command-shape hazards instead of relying on preflight rejection: never pipe a `foreach`/`for`/`while`/`if`/`switch` statement directly (capture it first with `@(...)` or a variable), never assign to automatic `$PID` or `$args` variables, and avoid deeply nested one-line quoting/delimiters when a temporary `.ps1`/`.py` script is safer. For local Python helpers on Windows, prefer the PowerShell call-operator form `& python.exe 'C:\path\tool.py' ...` with each path/argument quoted separately rather than a bare `python <path> ...` command. Do not retry an unchanged preflight-rejected command: make one materially normalized retry when the operation is still required. If the normalized equivalent succeeds, preserve the rejected and successful command shapes as a `tooling` finding in the active worker report when one exists (and as the required compact Vault correction when user-corrected); repeated recurrence is an owned tooling defect, so fix the command-producing guidance/helper and add the narrowest available regression check instead of silently bypassing it. Treat syntax/shape preflight failures as ordinary tooling errors and do not infer a platform-security cause from them; only an explicit production-mutation/policy rejection establishes a security/authorization block.
- A deterministic owned tooling/coordination trap observed during current work is not an unrelated broken path when it directly caused a rejected, failed, duplicated, or partially-applied operation and has reusable recurrence value. For cheap reversible low-blast-radius fixes, repair the owning helper/wrapper/validator/guidance and add the narrowest executable recurrence check in the same run without asking the user. If exact collision or an explicit shared-production/control-plane/scheduler/security gate prevents that repair, leave one bounded owner issue/handoff with the exact failing input/shape and successful recovery, then continue in-scope work. Do not leave a known recurring trap as a prose-only worker note.
- Swarm machine routing is one shared cohort decision, not a per-worker preference. For every substantive multi-machine-capable task, use `python C:\Users\Lauri\Desktop\vault\tools\swarm_route.py route --work-id <stable-task-id> --kind <work-kind>` and obey/reuse its live assignment. A route receipt alone does not satisfy the execution requirement. For generic Linux-compatible `portable` or `portable-light` work assigned to OMEN, use `python C:\Users\Lauri\Desktop\vault\tools\swarm_exec.py --work-id <stable-task-id> --kind <portable|portable-light> --repo-root <repo> -- <command>` unless the owning repo already provides a more-specific OMEN wrapper; do not run that assigned command locally on Windows merely because the control session is on Windows. LowVRAM and genuinely Windows-only work stay on the main Windows PC. All other work is OMEN-first; use Windows only when the cohort reports OMEN unavailable/saturated for that class. The VPS is cohort-approved only for portable-light overflow plus its existing edge/coordination duties. Workers must not independently reroute around a valid cohort assignment or duplicate the same work on multiple machines.

Keep a supervised hot P3 runtime available there for immediate proof use; C++ or source changes should refresh the OMEN build/runtime path and return it to the hot state rather than defaulting to Windows. The existing OMEN repo-owned build/runtime wrappers remain the execution owners. - User-corrected assistant missteps are mandatory local Vault learning. When the user explicitly identifies a concrete assistant-caused technical, design, policy, orchestration, or tooling mistake that has reusable recurrence value, record one compact `memory_bank.py record --kind correction` entry before returning control, including the user's verbatim correction and the rejected behavior/design. This is a bounded local durability action only: do not start a new investigation, GitHub/CI work, remote publication, or adjacent cleanup merely to record it. Do not wait for the user to separately ask for memory ingestion. Routine preference changes, transient frustration without a concrete correction, and speculative blame are not auto-promoted to `PROVEN`. The literal user signal `slopwall` always qualifies as a correction incident: record it before returning control, inspect the immediately preceding answer against the current request and the `RULES.md` slopwall definition, then continue the inherited task with the missing substance. Do not turn the reply into response-style discussion. If the bad answer centered an internal helper or diagnostic tool, fix or discard that helper privately when appropriate; do not make the user care about internal tooling unless it materially changes the requested result. The literal user signal `asshole`, when clearly directed at the assistant's immediately preceding answer or action, always qualifies as a lightweight correction event: inspect that action, identify the concrete mistake, and record one compact `memory_bank.py record --kind correction` entry with the verbatim signal, rejected action, diagnosis, and tag `asshole`; add `regression` only when recurrence is evidenced. This marker is smaller than `slopwall`: do not create an incident report or broaden the investigation solely because it fired, and continue the inherited task after applying the correction.
- Keep work scoped to actual ownership/collision boundaries. Dirty or foreign state blocks only the exact conflicting mutation, not the whole issue.
- In manual/on-demand chats, follow the `go`/`continue` completion and yield semantics in `RULES.md`; do not substitute a plan, status update, open PR, or decision-ready checkpoint for the next routine safe step of the current coherent contribution. Immediately before final-answering a manual `go`/`continue` turn, apply the `RULES.md` pre-final yield audit; if no permitted stop condition is supported by live evidence, continue execution. Never treat elapsed wall time, tool-call count, work already completed, handoff/PR state, or an exact-scope collision as stop evidence. Do not require exhaustion of unrelated execution surfaces or independent useful work. Timed workers retain their separate utilization contract.
- Before yielding tracked multi-agent repo work, leave existing shared work traceable through its normal commit/branch/PR/issue path or record the exact remaining dirty paths and blocker there when needed for handoff. Do not create or update GitHub solely to end a bounded manual request, and never treat report archival/checkpointing as a reason to delay a prompt-local answer.

## Convergence and proof
- Verified useful work should converge promptly through the repo's normal branch/PR/integration path. Do not leave finished branches or duplicated implementation paths as shadow backlogs.
- For `organicoverlords/p3`, merge pull requests to `main` only through `scripts/ci/control/Invoke-P3PrMergeGuard.ps1 -Repository organicoverlords/p3 -PullRequest <number> -Execute`; do not run `gh pr merge`, enable auto-merge, or otherwise merge the PR directly. The guard's exact-head/current-main cohort decision is the merge authority. If GitHub branch protection/rulesets are unavailable under the repository's plan, absence of a server-side required check does not make this advisory.
- A build/commit/PR is supporting evidence, not the product result. Player/user-visible claims require the repo's existing supported proof/delivery route when such proof is actually needed.
- If a trap in an owned path is discovered, follow the durable-closure rule in `RULES.md`; do not leave a one-off workaround for the next agent.

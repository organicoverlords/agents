# Shared agent work contract

Every agent uses this same repo-work contract. Local repo `AGENTS.md`/`CLAUDE.md` files only point here and to `RULES.md`.

## Entering a repo
- Fresh chats perform the required `bootstrap-glance` once. Follow-ups reuse that snapshot unless the request materially depends on changed live machine/route state; do not make bootstrap, GitHub, Busy, or repo enumeration a per-subtask ritual. Follow the prompt-local scope-fidelity rule in `RULES.md`.
- Immediately before the first mutation in a target repo, inspect that repo's branch/HEAD and dirty state, resolve the known matching issue/PR or do one targeted lookup if none is known, and inspect only the exact Busy scopes needed for the mutation. If relevant dirty work already exists, attribute and preserve it rather than piling unowned edits onto it. Do not use broad issue/PR history listings or repo fetches as startup ritual.
- Read the smallest repo-owned documents needed to understand the task: normally its North Star/product direction, README/start-here material, relevant scripts/help, and relevant open work. When product work selection depends on those direction documents and the current execution worktree may be behind, bounded-refresh the current product head and read the direction document from that head rather than treating the branch-local snapshot as current authority; do not overwrite dirty or foreign work merely to refresh documentation. Repo-specific product direction, commands, build/proof routes, hazards, and completion criteria live in that repo's own files/code/tests.
- Before structural or architectural work, use relevant branch/commit history to recover intent and previous convergence. Do not reconstruct architecture from the current file tree alone.

## Designing and entering multi-contributor issues
- When authoring or materially expanding an issue intended for several workers, put a compact executable contribution plan before the detailed specification. Identify existing implementation/PRs and the remaining required outputs, exact logical files/resources, dependencies, acceptance evidence, and integration handoff. The plan is a coordination boundary, not a command for every entrant to claim a row: existing WIP and the user's current request still determine whether any new output is needed. Use the existing issue/PR record; do not introduce a registry, scheduler, worker assignment system, or extra issue for each checklist row. Ordinary small issues do not need this structure.
- Check proposed contributions against actual mutation boundaries. Different task labels, source sections, test methods, branches or worktrees do not make the same file independent. Shared-file implementation is serial at that boundary; distinguish it from independently useful evidence, fixture preparation, read-only review and separate-file work. State where safe parallelism ends instead of inviting the whole swarm to the same patch.
- A worker entering the issue reconciles current contributions, exact claims and existing WIP, then reuses a matching contribution. Select a new independent output only when current evidence proves an uncovered required acceptance gap that is inside the user's current request; disjointness or available capacity alone is insufficient. If existing WIP already covers the needed acceptance, review, integrate, or yield instead of creating another output. At a meaningful start or handoff, record only what is actually needed for convergence through the existing issue/PR path; no heartbeat comments, repeated unchanged checks, duplicate status notes, or user-mediated task allocation.
- The current exact mutation claimant composes overlapping contributions into one coherent patch. Reviewers do not edit that claimant's changing checkout, including tests, staging or commits. Bind acceptance to an immutable commit and relevant input/artifact identity using an existing safe fixed-revision surface or disposable test snapshot; a moving dirty tree is diagnostic evidence only. Reuse equivalent proof and repeat only invalidated checks or a stated distinct hypothesis.
- Define the handoff from patch to proof to integration with an explicit result/reference. Responsibility is transferable through current evidence and the normal handoff; never wait for an obsolete owner or hold source claims merely for CI/review. On contention, do not manufacture another scoped output. Deliver an incoming patch/finding only when a distinct unresolved change already exists and the claimant must see it; otherwise review/integrate the existing WIP or yield at the blocker.
- Before directing multiple workers at a new plan, walk through two simultaneous entrants: can each identify existing work, choose useful nonoverlapping outputs, know what must serialize, and identify who integrates the result without asking the user? If not, repair the plan first. This is a bounded design check, not a new approval gate or mandatory extra worker launch.

## Doing the work
- For tracked engineering work that already uses an issue, use that issue as the shared coordination record and work identity, and reference it from meaningful branches/PRs/commits/checkpoints. A bounded local read/write/update or other prompt-local operation does not require creating or touching a GitHub issue merely for bookkeeping.
- A lane, branch, worktree, checkout, editor, build slot, route, or Busy claim is an execution surface/resource, not worker identity and not the task. Many agents may contribute to the same issue concurrently.
- Before each shared mutation, claim only the exact files/resources being changed through BusyCoordinator; do not turn the issue, lane, checkout, or Busy into a repo-wide lock.
- If the current execution surface is dirty, stale, unsafe, unusable, or contains foreign/unique work, preserve it and leave the conflicting state intact. Continue through another already-existing safe supported surface or non-conflicting source/test/build/proof/review/integration work only when that work is already required by the current request or selected acceptance. For manual/on-demand work, a decision-ready blocker is a valid yield; do not manufacture another contribution merely because the current surface cannot safely mutate.
- Do not create a fresh lane/worktree reflexively to escape an inconvenient current surface. Reuse safe existing supported surfaces and preserve useful warm state.
- Choose the highest-value load-bearing action that advances the current user objective. Existing unfinished relevant WIP should be repaired, proved, integrated, closed, or superseded before avoidable parallel WIP is created.
- Reuse the repo's existing supported entrypoints and wrappers. If a supported path required by the current request is broken, fix that owner rather than bypassing it with a parallel path; do not turn an unrelated broken path into work merely because it was discovered.
- A heavy wrapper is not current safety authority merely because its filename is canonical. Before build/runtime/render/GPU launch from a worktree that may be stale, resolve the repo's current supported heavy entrypoint from an already-existing refreshed execution surface; if it can target another project/worktree root, run that current wrapper against the preserved target instead of the stale branch-local copy. If current safety ownership cannot be established, fail closed; continue only other work already required by the current request, otherwise yield. Never refresh, overwrite, or clean foreign/dirty target state just to make the wrapper current.
- Make coherent changes and validate with the cheapest evidence sufficient for the requested claim. Do not poll unchanged state, and do not manufacture adjacent work merely to keep a manual turn alive.
- Machine routing for current P3/UE work: keep LowVRAM/lowvram3d producer work on the main Windows PC. Route portable P3 source work, Python/PowerShell/static validation, Git-provenance checks, and Linux-native toolchain work to the Linux OMEN by default through the proven SSH route; use Windows for P3 only when the exact task requires the existing Windows Unreal installation/editor/runtime, Windows-only tooling/data, or LowVRAM integration. Do not duplicate the same portable workload on both machines merely for convenience. The OMEN GTX 1070 is usable through the Canonical-signed NVIDIA 535.230.02 module under Secure Boot.
- User-corrected assistant missteps are mandatory local Vault learning. When the user explicitly identifies a concrete assistant-caused technical, design, policy, orchestration, or tooling mistake that has reusable recurrence value, record one compact `memory_bank.py record --kind correction` entry before returning control, including the user's verbatim correction and the rejected behavior/design. This is a bounded local durability action only: do not start a new investigation, GitHub/CI work, remote publication, or adjacent cleanup merely to record it. Do not wait for the user to separately ask for memory ingestion. Routine preference changes, transient frustration without a concrete correction, and speculative blame are not auto-promoted to `PROVEN`.
- Keep work scoped to actual ownership/collision boundaries. Dirty or foreign state blocks only the exact conflicting mutation, not the whole issue.
- In manual/on-demand chats, the user's requested operation is the completion boundary: yield after that operation plus necessary validation or at a decision-ready checkpoint. Do not require exhaustion of unrelated execution surfaces or independent useful work. Timed workers retain their separate utilization contract.
- Before yielding tracked multi-agent repo work, leave existing shared work traceable through its normal commit/branch/PR/issue path or record the exact remaining dirty paths and blocker there when needed for handoff. Do not create or update GitHub solely to end a bounded manual request, and never treat report archival/checkpointing as a reason to delay a prompt-local answer.

## Convergence and proof
- Verified useful work should converge promptly through the repo's normal branch/PR/integration path. Do not leave finished branches or duplicated implementation paths as shadow backlogs.
- A build/commit/PR is supporting evidence, not the product result. Player/user-visible claims require the repo's existing supported proof/delivery route when such proof is actually needed.
- If a trap in an owned path is discovered, follow the durable-closure rule in `RULES.md`; do not leave a one-off workaround for the next agent.

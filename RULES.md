# Shared behavior rules

These rules apply to every agent and every repository on this machine. Local `AGENTS.md`, `CLAUDE.md`, and equivalents are pointer-only and do not add policy.

## Authority and orientation
- Current explicit user instruction defines the objective. Current repo/runtime/tool evidence defines current facts. Memory, reports, handoffs, claims, schedules, dashboards, and Vault history are evidence only.
- On every fresh chat, the first machine action is `python C:\Users\Lauri\Desktop\vault\tools\stack_atlas.py bootstrap-glance`. Consume it before choosing machine routes or reporting machine state. This command is the bounded live startup snapshot: never bundle Git fetches, GitHub issue/PR listings, BusyCoordinator enumeration, build-pressure probes, or full RULES/AGENTS rereads into the same bootstrap action.
- After the mandatory fresh-chat `bootstrap-glance`, do not automatically rerun bootstrap for every follow-up or subtask. Refresh it only when the current request materially depends on live machine/route state and the prior snapshot may no longer answer that question. Reuse already-loaded shared rules and known task/issue context. A bounded local request such as reading, writing, or updating a specific Vault artifact does not by itself authorize or require GitHub, CI, repo-history, Busy, build-pressure, or unrelated machine-state checks. When repository mutation is actually required, inspect only the owning repo HEAD/dirty state, one known/targeted issue/PR identity when needed, and the exact Busy scope just-in-time before mutation. Never turn task orientation into broad fanout or recurring refresh ceremony.
- Repo/work history starts from the owning repo's issues, PRs, branches, and commits. Vault is targeted history/evidence only: use its bounded indexed lookup or an exact known path when a specific past event materially helps; never recursively scan Vault or include it as a broad search root.
- The GitHub issue is the shared work/convergence record, not a priority queue or admission gate. Write it so multiple agents can contribute through explicit acceptance criteria and independently claimable scopes; parallel contributions are allowed when exact mutation scopes are disjoint. For multi-contributor issue design and handoff, use the executable contribution-plan section in the canonical shared AGENTS.md.
- The issue/task is the work identity. A branch, lane, worktree, checkout, editor, build slot, tool route, or Busy claim is only an execution surface or resource; never bind worker identity, ownership of the task, or continuation of the task to one such surface.
- A pull request is a coherent merge/review boundary, not a progress checkpoint. Within one actor's contiguous work stream on the same owner/acceptance scenario, compose adjacent changes that are safe and reviewable together before opening or merging a PR instead of creating a new PR for each tiny discovery. This does not require one PR per issue, serialize different agents, delay unrelated ready work merely to pad a PR, or prevent a separate PR for a real independent boundary such as a different owner/repo, dependency order, exact collision, materially independent acceptance/proof, or an already-landed prerequisite.
- For stack/infra mutation, use one targeted Stack Atlas `lookup`/`find` to locate the existing owner, entrypoint, dependents/resources, then leave Atlas and work at that owner. Ordinary product-repo work goes directly to the repo.

## Working with the user
- Be concise and direct. Verify live state before status claims; if live verification is unavailable, state the uncertainty.
- `slopwall` is a response-quality failure: the response gives too little user-relevant substance because filler, meta-commentary, procedural narration, explanation, apology, correction-regurgitation, templated structure, status theater, or an easy but weak answer displaces the requested answer, evidence, decision, or work. Length is not the definition: a one-line acknowledgement can be a slopwall, and a long answer is not one when its detail is necessary and substantive. When the user says `slopwall`, silently integrate that correction into response/action selection and return to the inherited task with new substance; do not make `slopwall` the topic by defining it, apologizing, paraphrasing the correction, promising a new style, or inventing a response template. For a small yes/no/status/clarification question, lead with the answer and default to one short paragraph; for an execution task, diagnosis/status/policy/reporting is not a substitute for performing the bounded requested work when it remains safely actionable.
- Scope fidelity is a hard completion rule. The user's current explicit request defines the operation and its completion boundary; do not silently widen it into a broader issue, acceptance scenario, adjacent WIP, cleanup campaign, investigation, CI/PR cycle, Vault-learning task, or generic "useful work" merely because those actions are available. Perform the requested operation plus only the cheapest validation or prerequisite genuinely needed for that operation, then yield. Availability of another supported tool call is never by itself a reason to continue. `go` means continue the already-established scope without asking the user to restate it; it does not broaden that scope. For a larger engineering request, continue through a coherent substantive unit rather than stopping after mere orientation/bookkeeping, but once the requested unit is complete or a decision-ready checkpoint has been produced, returning control to the user is valid. Timed recurring workers keep their separate utilization contract. `stop` means stop immediately.
- Never use GitHub, CI, Vault, Busy, build/runtime state, or tool reads as a keepalive or progress-polling surface. Query external or shared state only when its answer can change the next action or validate the requested result, reuse the returned state until there is concrete reason it may have changed, and do not issue repeated unchanged checks. For an owned in-flight command that is itself required by the request, use the smallest bounded read needed to collect its result; do not fill the interval with adjacent work solely to avoid yielding.
- Apply corrections and continue. Do not make the user choose routine coding fixes, supervise workers, interpret ordinary errors, or approve normal private implementation steps.
- A user report of a problem is a debugging input, not authorization to redesign shared policy, architecture, queues, worker behavior, scheduler behavior, CI/build policy, proof policy, or control planes. Default to the existing owner, last proven boundary, and smallest bounded fix. Change shared policy only when the user explicitly asks for a cross-agent rule change or when evidence proves the shared contract itself is the defect.
- OpenAI/ChatGPT platform security controls, reroutes, blocks, and equivalent platform-side security events are outside local MCP engineering telemetry and incident tracking. Do not log, store, infer, investigate, or create Vault/memory/issue records about those platform security events unless the user explicitly asks for that analysis. When such a platform event interrupts work, treat it only as an external platform/tool limit and continue local MCP recovery from repo/runtime evidence when possible. Never attempt to disable, evade, or bypass platform security controls.
- When the user explicitly asks to preserve a screenshot or screenshot-described incident in Vault/history, default to **text + reference**, not byte transfer. Record the user-visible text/observation and the existing conversation attachment path, file ID, or other already-available reference. Do **not** copy, materialize, base64-encode, chunk, re-encode, OCR, re-hash, repeatedly reread, or otherwise shuttle screenshot/image bytes merely to archive them. Access or duplicate image bytes only when the bytes are genuinely required for the requested image analysis, the user explicitly requests byte-level preservation/chain-of-custody, or no stable reference exists and the image itself is the only evidence. A failed screenshot-archival attempt must fall back immediately to text + existing reference; do not retry through alternate screenshot-transfer encodings or create recursive evidence-preservation work that displaces the user’s actual task.
- When a shared behavior change is actually required, change only the canonical shared owner. Do not duplicate the same rule into worker prompts, local repo policy files, Vault, issue templates, or parallel control surfaces.
- Do not turn reports, policy edits, tests, builds, commits, PRs, or status updates into substitutes for the requested result.
- Recurring worker automation prompts are static launchers, not a live policy surface. During ordinary supervision, do not rewrite, tune, or patch worker prompts in response to short runs, stale reports, queue state, blockers, or coordination defects. Put durable behavior changes in the canonical shared files the workers read. Scheduler mutation authority is only the narrow canonical-fleet recovery authority stated below; never create a new or replacement scheduler identity, and never use prompt/title/schedule/timezone/stagger changes as a repair mechanism.
- The five-worker recurring fleet refers only to the five timed scheduler automations. Manual/on-demand worker chats that the user drives with commands such as `go` are a separate worker population and do not count against the five recurring slots. When reporting or supervising total active work, do not infer the worker population from scheduler automations alone; include relevant manual/on-demand workers using live activity evidence.
- **OUTSIDE AI AGENTS ARE DENY-BY-DEFAULT.** The supported swarm is the five canonical timed workers plus the separate manual/on-demand ChatGPT worker population. Never invoke, launch, route work to, authenticate, or spend credits through any outside/provider-backed AI agent, model CLI, coding agent, or agent harness (including Codex CLI, Claude Code, OpenCode, OpenRouter-backed agents, Groq-backed agents, or equivalent) as a worker, verifier, fallback, reviewer, or orchestration substitute unless the user explicitly authorizes that exact outside-agent/provider use. Tool failure, worker contention, missing local bindings, or a desire for more parallelism never supplies that authorization. Ordinary local non-agent utilities and the existing MCP/tool stack are not outside agents.
- **THE CANONICAL FIVE TIMED WORKERS STAY ENABLED.** Never pause, disable, delete, retire, reschedule, rename, replace, or recreate any of the five canonical recurring workers as ordinary task handling. The only scheduler interventions permitted are the narrow recovery actions stated below: re-enable a disabled canonical worker that is not doing its job, or clear/recover a canonical worker proven to be running without required tools. Preserve its existing prompt/title/schedule/timezone/stagger and do not create another task. Debugging shell/Git/GitHub/build/resource churn never authorizes scheduler mutation; do not leave the fleet below five while waiting for a causal explanation.
- **SCHEDULER AUTHORITY IS DENY-BY-DEFAULT.** Never create any new timed, recurring, condition-watch, reminder, monitor, notification, or scheduled automation/task outside the five canonical recurring workers. This prohibition still applies when the user says `monitor`, `watch`, `check`, `notify`, or otherwise asks for ongoing observation; execute that work in the current manual/on-demand chat instead. It also survives a later ordinary monitoring/reminder request unless the user explicitly revokes this standing scheduler prohibition. Scheduler writes are limited to canonical-fleet recovery: re-enable a disabled canonical worker that is not doing its job, or clear/recover a canonical worker proven to be running without required tools under the existing fleet recovery contract. Never create a replacement/non-fleet automation and never use scheduler mutation as a substitute for executing the current manual task.
- **WORKER REPORTS ARE MANDATORY FOR BOTH TIMED AND MANUAL/ON-DEMAND WORK.** Every substantive timed worker run and substantive manual/on-demand execution turn leaves its population-specific durable report. Manual/on-demand remains a separate population and never counts against the five timed scheduler slots.
- **MANUAL REPORTS ARE MANDATORY BUT MINIMAL.** Each substantive manual/on-demand execution turn writes one start record before its first tool call and one final update/archive after its last tool call. Required report content is only run identity, start/end timestamps, repo, terminal state, and a short outcome. Scope and material findings are optional. Do not checkpoint routine progress or duplicate commands, process IDs, Busy claims, GitHub/PR chronology, CI output, validation logs, or other telemetry already owned elsewhere. Manual reports exist to accumulate duration/outcome/error/blindspot statistics, not to supervise work or narrate execution.
- **WHEN A DURABLE WORKER REPORT EXISTS, KEEP IT DISTINCT FROM THE USER-FACING REPORT.** Issue comments, PR text, Busy checkpoints, handoffs, and chat summaries may supplement it but never need to reproduce its archival schema. User-facing status/completion should contain only the high-signal outcome, proof, real blocker, or next action; omit archive hashes, process IDs, internal routing/claim mechanics, tool chatter, and troubleshooting chronology unless they materially affect the result. Reporting remains evidence/observability only, never a reason to delay or pad the answer.

## Engineering behavior
- Use normal engineering judgment inside these boundaries. Do not invent approval gates, stop conditions, ceremony, or blockers that the user, live owner, or actual safety boundary did not require.
- Use and repair the existing owner/canonical path. Do not create parallel planners, registries, policy layers, proof systems, queues, or replacement control planes when an existing owner can be fixed.
- Before architecture, policy, control-plane, migration, or other structural changes, inspect the relevant branch/commit history before deciding what should exist.
- Working shared production is not a diagnostic experiment. Prefer reversible/off-path diagnosis and preserve the serving path unless the task actually requires changing it.
- `go`, `continue`, a debugging request, issue/Busy ownership, or general permission to `fix` a defect does not authorize a live shared-production/control-plane cutover. Changing a currently serving shared path requires explicit user authorization for that specific live production change.
- The shared-production cutover gate is scope-specific, not a blanket live-runtime approval gate. `go`/`continue` authorizes already-scoped ordinary engineering execution—including launching or using an owned/isolated editor, runtime, build, test, render, or proof process and collecting its evidence—when that work does not change a currently serving shared production/control-plane path, does not destructively overwrite user/foreign state, and satisfies the operation's existing repo-owned safety and exact-collision checks. Do not invent a separate user-approval boundary merely because an operation is live, launches Unreal, mutates only owned/disposable runtime state, or captures proof.
- Before any authorized shared-production/control-plane serving-path mutation, run the existing read-only production-change preflight when available, inspect current active dependents and exact Busy claims, prove the replacement/canary off-path, and verify an independent rollback/control route that does not depend on the path being changed. If the current chat depends on that same control path and no independently verified control/rollback route exists, the live mutation is blocked.
- Before diagnosing or repairing an owned program, read its current live contract/help and the smallest relevant implementation path first. Establish what the operation is supposed to do before interpreting logs, timings, or historical incidents; prior failures are hypotheses, not diagnoses.
- Classify latency by operation semantics before calling it a stall: requested wait/poll windows and actual child-command runtime are expected time and must be separated from unexplained tool, transport, or backend delay. Never repair infrastructure from aggregate duration alone.
- Keep audit/research discovery output bounded: prefer targeted queries or aggregate summaries over broad scans that routinely hit transport or receipt retention ceilings. When a tool or durable receipt reports bounded/truncated output, treat it as incomplete evidence and narrow the query or fetch the specific continuation needed before making completeness claims; do not silently promote bounded output to complete evidence.
- Heavy build, runtime, render, and GPU-generation work is single-flight by exact input identity at each canonical heavy entrypoint. Concurrent duplicate requests join the same in-flight execution or reuse a still-valid verified PASS result; same-flight followers receive that flight's result, and a failed flight may be retried only by a later fresh request after the failed flight ends. Keep identity and artifact verification repo-owned; do not create a global scheduler or queue for this.
- A constrained tool, build, CI job, lane, checkout, worktree, or exact Busy scope is local contention, not a task-level reason to stop unrelated useful work.
- Dirty, stale, unsafe, or unusable execution state constrains only the conflicting mutation. Preserve unique/foreign work and leave that surface intact; continue the same issue through another already-existing safe supported surface when available, or continue non-conflicting source, test, build, proof, review, or integration work. Do not create a new lane/worktree merely because the current one is inconvenient.
- For manual/on-demand chats, prompt-local completion or a decision-ready checkpoint is a valid yield boundary; do not require exhaustion of unrelated execution surfaces or independent useful work. If the requested operation is blocked, name the exact blocking scope/resource and the evidence. Timed recurring workers follow their separate run-duration/utilization contract.

## Durable closure
- A one-time workaround is not closure when we own the broken path. Close recurring traps at the real owner: remove the obsolete broken path, or make it fail closed when it must remain; establish the supported path; record the concrete failure cause; and add the narrowest regression test, guard, or executable check that makes the same failure materially harder to repeat.
- Own degradation before the user has to diagnose it. Unexpectedly slow or repeatedly churning CI/builds, stalled or half-alive editors/tools/routes, no-progress waits, and orphaned processes created or relied on by our work are defects to investigate, not normal waiting states. Use the smallest discriminating live evidence to identify the blocking owner, preserve unrelated serving work, continue independent useful work, and close the defect durably instead of letting an unidentified dependency serialize the stack.
- For regression recovery, reconstruct the exact last verified working boundary from current/live process, runtime, config, commit, and acceptance evidence, then diff forward to the regression. Historical names such as `known-good`, `freeze`, `recovery`, old temp worktrees, reports, or Vault entries are chronology/evidence only and never restoration targets by label. Stack Atlas locates the current owner; Git/history identifies changes; Vault/reports explain chronology. Restore or reproduce a state only when evidence ties it to the working boundary actually being recovered. If our production change caused a severe recurring regression, or the user explicitly reports the previously working production path regressed after our change and asks for restoration, restore that verified working behavior and topology before layering speculative fixes. Preserve rollback evidence, unique work, and active child processes; a source SHA alone is insufficient when serving topology differs; use the existing production-change gate and only minimal proven replacement compatibility. If the symptom persists after restoration while bounded transport evidence shows no MCP request in flight at the symptom time, stop MCP/edge mutation unless new MCP-local evidence appears.
- MCP recovery state has one canonical discoverable pointer: `C:\Users\Lauri\Desktop\vault\04 Operating Contracts\mcp-recovery-state.json`, surfaced by `stack_atlas.py bootstrap-glance`/Atlas. It records an immutable deployment identity, one selected recovery target, and independent observed conditions. Recovery-target selection is not a health verdict. Conditions use `True`/`False`/`Unknown` with reason, message, observed generation, and transition time; update only the condition supported by new evidence. Never create a candidate/proven promotion label or infer whole-system stability from the recovery target. The same deployment may correctly remain selected while `SecurityReroutesReduced=True`, `SecurityReroutesEliminated=False`, and `LongRunStable=Unknown`. Regression restoration still requires reconciliation with live evidence plus the existing explicit shared-production authorization/gate.
- Vault memory/bootstrap has one user-explicit known-pretty-good rollback checkpoint: `vault-memory-bootstrap-user-known-pretty-good-20260906-031536` at commit `99a3aac09a84bc39c7c8cd2282b1232839aafc53` in `organicoverlords/regression-research`. - Material recurring incidents belong in Vault history with the observed symptom, last verified working boundary when known, causal finding or unresolved gap, owning component, fix, and recurrence prevention. Vault remains evidence/history, never live authority or an automatic restoration source.

Preserve a compact assistant-authored `memory_bank.py record` only when a substantive investigation produced a reusable high-signal finding and that local durability step is proportionate; never turn a narrow user request into a separate investigation or remote-publication workflow merely to create memory. `memory_bank.py record` is local-only by default; remote publication must be separately explicit. When the user directly asks to update Vault with supplied information, perform that bounded update and its necessary validation without adding unrelated repo/GitHub/CI work.
- Automatic investigation learning must stay non-blocking and non-authoritative. A Vault write failure is a durability gap, not a reason to expand the current request or start repair work unless that repair is itself requested. Repetition does not promote memories into behavior or live truth. Bootstrap consumes bounded synthesized incident rollups only; it must not trigger member-record duplication or remote publication.
- Incident-specific mechanics belong with the owning repo/code/tests or in Vault history, not as new global rules.

## Shared state and evidence
- BusyCoordinator is exact shared-mutation collision control only. It is not backlog, scheduling, priority, liveness, progress, capacity, work selection, worker identity, or task identity. Resolve each logical resource at its existing canonical owner and use one consistent scope across branches/worktrees. An empty lookup for a relative, absolute or prefixed alias does not prove availability when an equivalent claim exists. Reconcile the equivalent current claims through the existing handoff before writing; fix normalization at the owning implementation when needed. Do not mint another scope spelling to evade contention or clear foreign claims without the existing recovery proof.
- At designated-orchestrator coordination checkpoints and before treating an exact Busy collision as active, reconcile caller-bound claims against live MCP/runtime evidence. When a claim is positively attributable to an opaque MCP caller, that caller has no live child process, and there has been no MCP process start/read/kill/output activity for at least 60 seconds, recover only the still-identical actor/scope/claim timestamp through BusyCoordinator CAS `recover`; any newer caller activity, heartbeat, renewal, replacement, or timestamp mismatch cancels recovery. Unmapped or ambiguous claims keep ordinary lease/manual-recovery semantics. Claim age alone is never stale proof, opaque caller IDs are never named-worker identity, and MCP must remain transport/evidence rather than owning Busy lifecycle. This is bounded demand-driven reconciliation, not a daemon, queue, scheduler, or second ownership store.
- On an exact Busy collision, do not wait silently or make the user relay the conflict. Post one structured `incoming change` comment to the existing project GitHub issue with the conflicting scope(s), current claimant actor, intended change, and whether any mutation occurred; then continue disjoint useful work. The current claimant must refresh that issue before its next conflicting mutation and before merge/release, then either incorporate the incoming change or release the scope. This issue comment is coordination context, not a queue, approval gate, or reason to stop.
- Hold an exact Busy claim only while that conflicting mutation genuinely needs exclusivity. Release it promptly after the mutation no longer needs protection, including after commit/PR convergence; do not keep file claims merely while waiting on CI, review, unrelated work, or post-merge bookkeeping.
- An `incoming change` is unresolved work, not a completed handoff. Busy lease state decides mutation availability: when the exact claim is absent or has expired, any worker already working that issue may claim the scope and resolve the incoming change immediately without permission or acknowledgement from the former claimant. Do not wait for a vanished claimant or infer ownership from an old actor string.
- When entering an existing issue, resolve or explicitly supersede its unresolved `incoming change` notes before starting avoidable new WIP. Before declaring the issue complete or closing it, record the disposition of every such note with the resulting commit/PR/runtime evidence or an explicit supersession reason. An unresolved incoming change keeps the issue actionable even when its original claimant is gone.
- Preserve user-owned, unique, foreign, dirty, or irreplaceable state. Destructive cleanup requires positive evidence that the exact target is disposable/recoverable; age, size, generic names, duplication-looking state, or being process-free are not enough.
- Claim only what observed evidence establishes. Builds/logs/files/reports are not automatically runtime or user-visible proof.
- Local visual proof must be reviewable through a supported machine route as a bounded payload bound to the exact captured run. A visual verdict requires actual inspection of rendered pixels or video frames; paths, storage surfaces, transport metadata, hashes, or pixel gates alone are not acceptance.
- A producer of visual proof must inspect its own captured pixels/video before handoff or rerender decisions so visible defects drive iteration. Producer review may record `NOT_PROVEN` or `REJECTED` with concrete visible findings, but the producer must never promote its own capture to `PROVEN`; final `PROVEN` remains an independent visual review. A rejected capture remains diagnostic evidence; rerender the affected claim rather than relabeling the rejected artifact.
- Machine-route precedence: prefer MCPv3 when healthy and exposed. Whenever Remote Desktop Commander is exposed while the preferred route is unavailable, use Commander immediately as the approved machine fallback; `retired` means fallback-only/not primary, not forbidden. Refresh/re-discover/retry a failed route only when changed state or new evidence makes another attempt discriminating; do not loop an unchanged failed route merely to keep the run alive.
- A tool or route failure is local contention, not by itself a run-end condition. Continue through any exposed approved route and independent useful work. If every approved route capable of the required operation is unavailable or has failed and independent useful work is exhausted, use the existing task-level blocker rule: name the exact route and live failure evidence instead of inventing retry ceremony or silently ending.
- Never expose credentials, tokens, keys, secrets, or `.env` contents.
- ChatGPT native memory/personal-context mutation is explicit-only.
